Homepage projects use the existing `featured` boolean. Select at most three published projects: featured first, newest `created_at` first within each group, then ascending ID for ties. Fill unused slots with the newest unfeatured projects. Zero published projects yields an empty section. Titles never influence selection. Creation timestamps are never edited for curation.

`selectHomeProjects` is shared by the browser and prerenderer. Project create/edit exposes “Featured on homepage”, retains it when other fields change, and invalidates project queries after saving. The archive remains available at `/projects`; the homepage limit does not apply to it. Static HTML reflects the last build; prerender snapshots are marked stale so a browser refetch sees subsequent admin changes immediately on navigation. Updating static HTML requires a separate authorized build/release.

The access candidate has this role/action contract:

| Action                                                   | Anonymous / ordinary user / user-metadata admin     | Authorized admin                                           | Service                           |
| -------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------- | --------------------------------- |
| Read posts and published projects                        | Allow                                               | Allow, including draft projects                            | Allow                             |
| Create/update/delete posts and projects                  | Deny                                                | Allow                                                      | Allow                             |
| Subscribe                                                | Email-only insert; defaults supply protected fields | Email-only insert; may manage existing subscribers         | Allow                             |
| Read/change subscribers, email queue and email analytics | Deny                                                | Allow                                                      | Allow                             |
| Read visitor analytics, cursor preferences and summary   | Deny                                                | Allow                                                      | Allow                             |
| Write visitor analytics directly                         | Deny                                                | Deny                                                       | Allow                             |
| Submit telemetry                                         | Bounded append-only RPCs, browser consent required  | Same consent requirement                                   | Allow                             |
| Update telemetry duration or enrich existing rows        | Deny                                                | Geolocation endpoint requires verified admin authorization | Allow through trusted server code |

Authorization matches the existing server helper: the established owner UID or `app_metadata.role = 'admin'`. The Auth Admin API may provision app metadata only from trusted server credentials; users' editable `user_metadata` never authorizes access. Refresh tokens after a role change; already-issued JWT authorization can remain valid until expiry. No privileged credential belongs in the browser.

The shared admin route checks verified users before mounting any admin page and denies ordinary authenticated users explicitly. Mutations that can silently affect zero rows request a single returned record, so denial becomes a visible error rather than a success toast. Database policies remain the authorization boundary.

Public telemetry is intentionally append-only. Repeated session IDs cannot change existing sessions; page-view inputs are bounded and require a valid path/session. Public duration updates and automatic geolocation enrichment are removed. New records therefore have no measured duration or automatically enriched location; last activity remains the session creation time. Anonymous ingestion can still be spammed and cannot prove that a caller obtained consent; rate limiting and stronger ingestion identity would require a separate service. Existing metrics retain their stored values. Signup still reveals duplicate email status, matching the current form.

Candidate rollout is owner-controlled and separate from these issues. Test the migration and client together in an isolated Supabase environment; do not blindly replay historical migrations, which contain production content changes. Ship the updated client and restrict the geolocation function as part of the coordinated release, then apply only the reviewed forward migration. Keep geolocation closed to public callers throughout rollout. Inspect workflow triggers before pushing: `.github/workflows/deploy.yml` deploys `main`/`master` to `gh-pages`; the build poststep can deploy functions when `SUPABASE_DEPLOY` is enabled.

Recovery: migration statements are transactional. A failure rolls back the entire migration. After a successful application, fix forward while retaining RLS and revoked public update grants. If ingestion misbehaves, revoke client EXECUTE on the two ingestion RPCs, accepting a telemetry gap; do not restore public table writes, duration updates, or private reads. Keep the previous public client only if its constrained-ingestion compatibility has been tested. Rebuild static pages separately when the owner approves content/release work.
